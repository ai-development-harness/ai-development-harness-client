## Findings

- **F-001 — High — Принятая data-only filesystem boundary не является atomic/no-follow.**
  - Location: `docs/adr/ADR-004-bezopasnaya-git-worktree-proektsiya.md:19-23,43-45`; `apps/local-service/src/repository-projection.ts:26-32,57-67`.
  - Scenario: selected root считается untrusted, но loader сначала выполняет `lstat(target)`, а затем отдельный `readFile(target)`. Между операциями владелец каталога заменяет проверенный regular file на symlink или FIFO; `readFile` следует уже новому path. ADR относит atomic no-follow только к будущей Git capability, хотя текущая repository projection прямо продолжает читать untrusted data artifacts.
  - Impact: принятый ADR объявляет ограниченную безопасную boundary, которая допускает local file read за пределами root и неограниченную блокировку local service при concurrent replacement. Это не закрывает filesystem/subprocess denial-of-service часть threat model и не обеспечивает заявленное safe MVP behaviour.
  - Fix direction: закрепить atomic no-follow и root-identity semantics именно для текущей data-only projection; читать через открытый с `O_NOFOLLOW` descriptor, проверять type/size через `fstat` того же descriptor, ограничивать чтение и обрабатывать replacement fail closed. Добавить regression на swap regular file в symlink/FIFO либо явно изменить threat model и task contract, если concurrent mutation сознательно не поддерживается.

- **F-002 — High — Migration path Git capability не связан с фактическим MVP-owner STEP-013.**
  - Location: `docs/adr/ADR-004-bezopasnaya-git-worktree-proektsiya.md:23,35-37,53-58`; `planning/tasks/STEP-013.md:1-35`; `planning/tasks/STEP-015.md:1-26`.
  - Scenario: ADR разрешает worktree/metadata только отдельному STEP с explicit capability contract и security review. Реальный MVP STEP-013 владеет `Git projection, commands/chains, blockers`, но содержит только ADR-001 и risk `external-integration`; ADR-004 вместо него trace-ит STEP-015 про hosted local bridge, хотя сам ADR говорит, что hosted bridge не меняет решение.
  - Impact: roadmap не содержит проверяемого владельца обязательной sandbox/capability boundary для REQ-008. При планировании STEP-013 разработчик может снова вызвать Git над untrusted root без security-sensitive orchestration и формально не нарушить его текущий task contract.
  - Fix direction: сделать traceability ADR-004 ↔ STEP-013 двусторонней, добавить `security-sensitive`/`architecture` и явный prerequisite capability/security decision в STEP-013 либо создать отдельный prerequisite STEP и dependency. Удалить STEP-015 из ADR-004 или синхронизировать его contract только если hosted bridge действительно затронут решением.

- **F-003 — Medium — Dependency/contract correction STEP-002 и roadmap projection остались противоречивыми.**
  - Location: `planning/tasks/STEP-017.md:87`; `planning/tasks/STEP-002.md:24-26,55-66,90-102`; `planning/PLAN.md:22,30`.
  - Scenario: implementation plan STEP-017 требует обновить acceptance/verification/rollback STEP-002 под policy `SECURITY_POLICY unavailable`. Фактически acceptance всё ещё требует, чтобы service читал `project artifacts/Git`, deliverable/goal остаются Git projection без оговорки unavailable, а последнее evidence утверждает чтение Git toplevel/upstream/divergence, уже удалённое текущей реализацией. Одновременно PLAN рекомендует `STEP PLAN STEP-017`, хотя task уже имеет `Plan status: Ready` и выполняется через `STEP RUN`.
  - Impact: следующий reviewer/implementer получает два несовместимых контракта и может либо вернуть запрещённый Git subprocess, либо принять недоказанные Git facts; projection предлагает уже выполненную команду и расходится с STATUS.
  - Fix direction: привести acceptance, verification, deliverables и compatibility/rollback STEP-002 к typed policy-unavailable contract; историческое evidence не переписывать как новый факт, а явно отметить superseded observation и записать актуальную проверку отсутствия production Git subprocess. Синхронизировать рекомендуемое действие PLAN с task/STATUS.
