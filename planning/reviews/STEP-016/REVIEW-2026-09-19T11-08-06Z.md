## Findings

### F-001 — HIGH — Yarn install state записывается в host working tree

**Location:** `.yarnrc.yml:2-3`, `compose.yaml:16-29`, `.gitignore:28`
**Scenario:** Given repository root смонтирован в `/workspace` через writable bind mount и Yarn использует `node-modules`, when container выполняет `yarn install`, then Yarn создаёт `/workspace/.yarn/install-state.gz` непосредственно на host. Файл фактически присутствует в checkout после заявленной container install.
**Impact:** Не выполнен acceptance criterion, по которому dependencies и development caches не должны записываться в host working tree. Игнорирование файла Git не обеспечивает требуемую filesystem isolation.
**Fix direction:** Перенести `installStatePath` в отдельный container-only path с named volume либо изолировать `/workspace/.yarn` отдельным named volume. После исправления выполнить install с чистыми volumes и доказать отсутствие нового dependency/cache state в host checkout.

### F-002 — HIGH — Скрипты запуска доверяют CWD и внешнему Compose selection

**Location:** `start.sh:4-10`, `stop.sh:4-10`
**Scenario:** Given пользователь запускает абсолютный или относительный путь к repository script из другого каталога либо имеет унаследованный `COMPOSE_FILE`, when script вызывает `docker compose` без явных `-f` и `--project-directory`, then Compose может выполнить конфигурацию текущего каталога или указанную окружением вместо repository `compose.yaml`.
**Impact:** `start.sh` способен запустить чужую Compose-конфигурацию с Docker-equivalent привилегиями, а `stop.sh` — остановить посторонний проект. Это нарушает предсказуемость root scripts и создаёт путь к host modification.
**Fix direction:** Надёжно определить physical directory самого script и вызывать Compose с явными `--project-directory "$SCRIPT_DIR" -f "$SCRIPT_DIR/compose.yaml"`; добавить regression-проверку запуска script из другого каталога и при внешнем `COMPOSE_FILE`.

### F-003 — MEDIUM — Vite опубликован на всех host interfaces

**Location:** `compose.yaml:10-11`, `apps/web/vite.config.mts:8-12`
**Scenario:** Given developer host подключён к общей или недоверенной сети, when Compose публикует `4200:4200` и Vite слушает `0.0.0.0` внутри container, then dev server доступен по non-loopback адресу host.
**Impact:** Другой участник сети может открыть unauthenticated development UI и получить отдаваемые Vite source modules/source maps. Риск будет усиливаться по мере появления privileged Harness actions.
**Fix direction:** Оставить container listener на `0.0.0.0`, но публиковать только `127.0.0.1:4200:4200`; проверить loopback-доступность и отсутствие доступа через non-loopback host address.

### F-004 — MEDIUM — Container process создаёт чужие artefacts в source bind mount

**Location:** `Dockerfile:2-9`, `compose.yaml:16-35`
**Scenario:** Given image не задаёт `USER`, when automatic `local-service:serve` build или документированные build gates пишут в bind-mounted checkout, then outputs создаются от container root/remapped UID. После реализации `apps/local-service/dist` и часть `apps/web/dist` фактически принадлежат `nobody:nogroup` и имеют каталоги `0755`/файлы `0644`.
**Impact:** Host developer может получить недоступные для изменения/очистки build artefacts; writable bind mount также даёт lifecycle/dev processes возможность менять repository files и читать local-only data с избыточными привилегиями.
**Fix direction:** Запускать service под согласованным non-root host UID/GID и минимизировать writable bind surface; при необходимости выделить generated outputs в отдельные writable volumes. Добавить проверку UID и ownership создаваемых artefacts.

### F-005 — MEDIUM — Nx prune target сохранил npm-specific output после Yarn migration

**Location:** `apps/local-service/package.json:45-54`
**Scenario:** Given root package manager теперь Yarn, when `local-service:prune-lockfile` выполняется и затем восстанавливается из Nx cache, then executor создаёт `dist/yarn.lock`, но declared outputs по-прежнему включают только `dist/package-lock.json`.
**Impact:** Nx cache не сохраняет и не восстанавливает фактический pruned Yarn lockfile, поэтому существующий packaging target выдаёт неполный cached output. Миграция package-manager contract завершена не во всех package-manager-specific настройках.
**Fix direction:** Заменить npm-specific output на `{workspaceRoot}/apps/local-service/dist/yarn.lock` и проверить uncached и cached execution `local-service:prune-lockfile`.

### F-006 — HIGH — Обязательный live reload `local-service` не доказан

**Location:** `planning/tasks/STEP-016.md`, разделы `Verification` и `Evidence`
**Scenario:** Given Verification требует live reload обоих development processes, when рассматривается сохранённое evidence, then host-правка и reload зафиксированы только для `apps/web/src/main.tsx`/Vite; для `local-service` отсутствуют host-правка, rebuild/restart log и наблюдаемый эффект.
**Impact:** Один из обязательных runtime gates не закрыт, а одновременная жизнеспособность обоих `serve` targets после source change не подтверждена.
**Fix direction:** В чистом запущенном environment изменить `apps/local-service/src/main.ts` на host, зафиксировать Nx rebuild и restart/новый process output, восстановить файл и подтвердить, что web и local-service targets продолжают работать одновременно.

### F-007 — MEDIUM — Чистая immutable container install не подтверждена воспроизводимым evidence

**Location:** `planning/tasks/STEP-016.md`, разделы `Verification` и `Evidence`
**Scenario:** Given Verification требует чистую Yarn install с immutable lockfile именно в container, when рассматривается evidence, then указана только команда `corepack yarn install --immutable` без container invocation и без зафиксированного clean state named volumes.
**Impact:** Evidence не отличает host install или повторное использование уже заполненных volumes от требуемого clean container scenario.
**Fix direction:** После контролируемой очистки только STEP-016 development volumes выполнить и зафиксировать точную `docker compose run/exec ... corepack yarn install --immutable` command, exit code и clean-volume precondition.

### F-008 — MEDIUM — Документированные individual serve commands конфликтуют с уже запущенными targets

**Location:** `docs/development.md:29-37`
**Scenario:** Given `./start.sh` уже запускает `web:serve` и `local-service:serve` в service `dev`, when пользователь выполняет документированный `docker compose exec dev corepack yarn nx run web:serve`, then второй Vite process пытается занять уже используемый port 4200 и завершается ошибкой.
**Impact:** Раздел `Development commands` не описывает фактически исполнимый workflow и ведёт пользователя к ошибке в штатно запущенном environment.
**Fix direction:** Удалить дублирующие serve commands либо заменить их на корректные команды наблюдения/диагностики (`logs`, status); individual serve workflow документировать отдельно с явной остановкой общего process или отдельным one-off service без port conflict.
