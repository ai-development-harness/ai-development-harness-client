## Findings

### F-009 — HIGH — Внешний `COMPOSE_PROJECT_NAME` всё ещё меняет целевой Compose project

**Location:** `start.sh:4-13`, `stop.sh:4-13`, `compose.yaml:1`
**Scenario:** Given в shell, `direnv`, wrapper или CI задан `COMPOSE_PROJECT_NAME`, when пользователь запускает `./stop.sh`, then Compose применяет `down --remove-orphans` к подменённому project name. Явные `--project-directory` и `-f` не отменяют этот environment override: проверка `COMPOSE_PROJECT_NAME=untrusted docker compose --project-directory "$PWD" -f "$PWD/compose.yaml" config --format json` вернула `"name": "untrusted"`.
**Impact:** Скрипт может остановить и удалить containers/network другого Compose project; `start.sh` создаёт ресурсы не под документированным именем. Поэтому `F-002` закрыт только для caller CWD и `COMPOSE_FILE`.
**Fix direction:** Передавать фиксированный `--project-name ai-development-harness-client-dev` обоим scripts либо перед вызовом Compose также очищать `COMPOSE_PROJECT_NAME`; regression должен одновременно покрыть внешний `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME` и запуск из другого CWD.

### F-010 — HIGH — `dev` сохраняет write access ко всему checkout, включая `.git`

**Location:** `compose.yaml:51-55`
**Scenario:** Given dependency/plugin либо один из development processes скомпрометирован, when он работает под container user `node` с UID/GID `1000/1000` на текущем host, then writable root bind mount разрешает изменить tracked source, root scripts и `.git/hooks`. `cap_drop`, `no-new-privileges` и non-root user не ограничивают обычную запись в файлы того же UID.
**Impact:** Вредоносное изменение переживает удаление container и может выполнить код уже на host при последующей Git/package operation. `F-004` устранил root-owned artefacts на текущем host, но не заявленную избыточную writable bind surface.
**Fix direction:** Монтировать checkout read-only, а доказанно необходимые writable outputs (`dist`, test output и другие generated paths) вынести в named volumes; `.git` и local-only secrets не должны быть доступны runtime process без необходимости. Проверить, что host edits по-прежнему видны watcher-ам, gates проходят, а запись из container в tracked source и `.git` запрещена.

### F-011 — MEDIUM — Named volume `yarn-cache` не используется Yarn

**Location:** `.yarnrc.yml:3`, `compose.yaml:46-64`
**Scenario:** Given `.yarnrc.yml` задаёт `enableGlobalCache: true`, when Yarn 4.18.0 получает `YARN_CACHE_FOLDER=/yarn-cache`, then effective `cacheFolder` остаётся внутри `globalFolder`, а не в `/yarn-cache`. Read-only проверка тем же Yarn показала, что override не меняет effective cache path; в container это будет каталог под `/home/node/.yarn/berry`, находящийся в writable container layer.
**Impact:** Объявленный `yarn-cache` volume не сохраняет package cache между `docker compose down`/новым container, а документация ошибочно обещает сохранение Yarn cache. Это нарушает Scope и Docker workflow contract об отдельном named volume для Yarn cache.
**Fix direction:** Либо отключить global cache и явно направить `cacheFolder` в `/yarn-cache`, либо монтировать effective Yarn `globalFolder` в named volume. Зафиксировать `yarn config get cacheFolder` внутри container и содержимое соответствующего volume после clean install и restart.

### F-012 — MEDIUM — Cache behavior исправленного `prune-lockfile` не проверено

**Location:** `apps/local-service/package.json:45-54`, `planning/tasks/STEP-016.md:117`
**Scenario:** Given `prune-lockfile` имеет `cache: true` и finding `F-005` относился именно к сохранению/восстановлению Yarn lockfile через Nx cache, when рассматривается новое evidence, then выполнен только `--skip-nx-cache` run. Он доказывает создание `dist/yarn.lock`, но не его включение в cache artefacts и восстановление при cache hit.
**Impact:** Исправленный declared output выглядит корректно, но исходный regression scenario остаётся непроверенным; packaging target может снова выдавать неполный cached output без обнаружения.
**Fix direction:** Выполнить clean uncached run, удалить generated output, затем повторить target с Nx cache и подтвердить cache hit и восстановленный `apps/local-service/dist/yarn.lock`.

### F-013 — MEDIUM — Сохранение нового `yarn-state` volume после `stop.sh` не доказано

**Location:** `planning/tasks/STEP-016.md:112-115`, `compose.yaml:63-64`
**Scenario:** Given исправление `F-001` добавило отдельный `yarn-state` volume, when рассматривается runtime evidence остановки, then `docker volume inspect` перечисляет только `node_modules`, `yarn-cache` и `nx-cache`; новый `yarn-state` после `./stop.sh` не проверен.
**Impact:** Обязательный verification gate сохранения named volumes и документированное обещание сохранения Yarn install state не подтверждены для нового состояния реализации.
**Fix direction:** После clean start и успешной install выполнить `./stop.sh`, проверить существование и содержимое всех четырёх volumes, включая `yarn-state`, затем повторно запустить environment без очистки.
