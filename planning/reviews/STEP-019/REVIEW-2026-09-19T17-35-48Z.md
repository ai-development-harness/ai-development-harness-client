## Findings

### F-S10 — High — `TEARDOWN` не запрещает позднее присоединение worker к уже очищенному unit

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:31,35-39`; `planning/tasks/STEP-002.md:65,83,86`

**Scenario:** Given attach worker был начат для `BOUND`/`ACTIVE` unit и завис либо завершался конкурентно, when supervisor durable фиксирует `TEARDOWN`, выполняет kill-all, получает empty proof, освобождает lease и удаляет record, then ADR не требует fence/seal, который запрещает завершение старого attach после empty proof. Delayed attach с прежним handle/owner может добавить process в unit уже после доказанного empty state и release capacity.

**Impact:** новый admission переиспользует budget одновременно с живым residual worker; crash-consistent accounting и гарантия «empty before release» обходятся корректной, но небезопасной interleaving без PID/timeout ошибок.

**Fix direction:** определить owner generation/fencing token, привязанный к `unitKey`/nonce и lease; перед kill-all атомарно закрывать unit для новых members либо отзывать прежнее поколение, дожидаться всех in-flight attach и только затем получать authoritative empty proof. Удаление/destroy unit должно исключать повторный attach через stale handle. STEP-002 должен получить deterministic interleaving regression `attach pending → TEARDOWN/seal → empty proof/release → delayed attach`, доказывающий отказ stale operation и отсутствие capacity reuse.

### F-A12 — High — Activation boundary не задаёт fail-closed recovery worker, присоединённого до `ACTIVE`

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:31,35,47,75`; `planning/tasks/STEP-002.md:65,83,86`

**Scenario:** Given worker уже inertly attached и membership verified, but durable record всё ещё `BOUND`, when supervisor падает до/после неназванного `release barrier` и перезапускается, then recovery видит `BOUND` с существующим member. ADR запрещает новый worker, но не определяет, обязан ли recovery teardown-ить member, как доказывается его inertness после parent death и какая durable операция линейно предшествует разрешению untrusted I/O. Условие «не допускать I/O до verified `BOUND`» уже выполнено и поэтому само по себе не удерживает worker.

**Impact:** worker может начать untrusted filesystem I/O без durable `ACTIVE`, либо навсегда удержать lease без определённого recovery path. Acceptance STEP-019 о порядке persistence/attach и recovery каждого interrupted state не доказан.

**Fix direction:** определить отдельный durable activation protocol: fail-closed worker gate с generation/token, однозначный порядок `attach → membership proof → durable ACTIVE/activation intent → one-shot release`, поведение parent death и recovery `BOUND` с уже существующим member. Добавить crash injections до и после durable activation и до/после release signal с проверкой, что untrusted I/O невозможно до committed active state.

### F-A13 — High — После reap нет durable proof, который новый supervisor может восстановить перед release

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:26,35-39`; `planning/tasks/STEP-019.md:45-47,87`; `planning/tasks/STEP-002.md:65,83`

**Scenario:** Given `TEARDOWN` записан, unit authoritatively empty и прежний supervisor уже reaped direct child, when он падает до начала/commit release transaction, then новый supervisor видит только `TEARDOWN`. Empty proof можно повторить, но факт direct-child reap прежним process нельзя повторно получить или надёжно вывести из отсутствия PID/record; отдельного durable `REAPED/CLEANED` checkpoint либо supervisor-independent reaper attestation нет.

**Impact:** recovery должен либо удерживать lease навсегда после обычного crash, либо освобождать его без обязательного reap proof. Это нарушает заявленную завершаемость exactly-once release и оставляет критический crash window непосредственно перед transaction.

**Fix direction:** добавить durable terminal checkpoint/receipt, атомарно связывающий authoritative empty proof и подтверждение reaper с `unitKey`/nonce/lease generation, либо обязать platform profile предоставлять supervisor-independent идемпотентный reap proof. Затем определить ABA-safe release/tombstone semantics, чтобы replay старой transaction не освобождал новый lease.

### F-T09 — High — Test handoff не покрывает crash-consistency release transaction

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:37,45-49`; `planning/tasks/STEP-002.md:69,83,86`; `planning/tasks/STEP-019.md:45-47,88`

**Scenario:** Given tests inject crash только после `RESERVED`, создания unit, binding handle, attach worker и записи `TEARDOWN` перед kill-all, when crash происходит после empty proof/reap до release transaction, на границе durable release и удаления lifecycle record либо после commit/delete перед подтверждением recovery, then обязательного regression нет. Формулировка «exactly-once release» без этих fault points может пройти при реализации, допускающей partial release/delete, double release или premature reuse.

**Impact:** future suite не докажет основную новую гарантию ADR-007 на самой опасной terminal boundary; F-S09 может быть устранён на admission, но эквивалентный reuse window останется на teardown.

**Fix direction:** расширить ADR-007 и STEP-002 parameterized crash matrix точками после empty proof/reap до transaction, во время commit с доказательством отсутствия наблюдаемого half-applied состояния и после commit/delete до acknowledgement. На каждом restart проверять retained budget до valid proof, отсутствие нового spawn, одну release для исходной lease identity и невозможность старому replay освободить новый lease.

## Verdict rationale

ADR-007 устраняет исходный admission crash window, задаёт fail-closed damaged-record recovery и закрывает opaque-observation handoff. Однако lifecycle остаётся небезопасным на двух соседних concurrency boundaries: worker activation между `BOUND` и `ACTIVE` и teardown без fencing новых members. После reap также нет durable доказательства, которое restart может использовать перед release, а STEP-002 не обязан тестировать terminal transaction fault points. Поэтому acceptance crash-consistent lifecycle и exactly-once lease release не доказаны; verdict — `FAIL`, ADR-007 нельзя переводить в `Accepted`, а STEP-002 нельзя разблокировать.
