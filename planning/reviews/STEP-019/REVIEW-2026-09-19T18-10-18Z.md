## Findings

### F-A18 — High — Нет fencing для конкурирующего или отложенного создания unit

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:29,43,49,53-57,65-69`; `planning/tasks/STEP-002.md:83-87`.

**Scenario:** Given создание unit из `RESERVED` началось, но ещё не стало видимо recovery, when cancellation/restart переводит record в `TEARDOWN`, получает proof отсутствия unit/child, создаёт terminal receipt и освобождает lease, then старое create может завершиться после release и создать discoverable unit с прежними `unitKey`/nonce. Требование exclusive/idempotent create не запрещает первое позднее завершение, а generation fence определён только для activation/attach.

**Impact:** admission budget уже переиспользован при существующем orphan unit; следующий startup вынужден блокировать admission, а crash-consistent accounting нарушается на исходной admission boundary F-S09.

**Fix direction:** определить общую linearization/fencing boundary create против `TEARDOWN`: durable `creationIntent`, generation-bound create и terminal proof, что старое create больше не может завершиться, либо profile-level синхронный primitive с тем же postcondition. Добавить deterministic regression `create pending → TEARDOWN/receipt/release → delayed create`.

### F-A19 — High — Не определены single-writer ownership и concurrent startup recovery

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:23,29,35-37,53-57`; `planning/tasks/STEP-019.md:62-64`; `planning/tasks/STEP-002.md:65,83-87`.

**Scenario:** Given два local-service/supervisor process запускаются одновременно либо новый process стартует до доказанной смерти прежнего owner, when оба authoritatively enumerate state и открывают admission, then capacity check и запись `RESERVED` не обязаны быть одной global linearizable transaction. Второй supervisor также может принять живой `ACTIVE` первого за recovered и начать teardown: `ownerGeneration` присутствует в payload, но owner claim, takeover CAS, singleton lease либо fence прежнего owner не определены.

**Impact:** возможны превышение admission limit, teardown живого request и конкурирующие recovery/release operations. ABA-safe tombstone защищает отдельную release transaction, но не global admission/recovery epoch.

**Fix direction:** закрепить доказанный single-supervisor invariant либо durable global supervisor epoch/lease. Capacity check + `RESERVED` должны быть одной linearizable transaction; takeover разрешён только после fencing прежнего owner, а startup enumeration и открытие admission должны принадлежать одному recovery epoch. Добавить regressions с двумя overlapping supervisors.

### F-A20 — Medium/High — Полное supersede ADR-006 теряет неперенесённые действующие контракты

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:6,19,89-99`; `docs/adr/ADR-006-containment-boundary-repository-projection.md:15-21,39-47`; `planning/tasks/STEP-019.md:65,75,90-91`.

**Scenario:** Given после PASS ADR-006 планируется отметить superseded и сделать ADR-007 current traceability, when implementer восстанавливает current architecture contract, then ADR-007 заменяет только containment lifecycle и не инкорпорирует остальные решения ADR-006: bounded lexical-only parent validation, descriptor-first identity, обязательные capability/resource limits, trusted spawn profile, immutable caller settlement и success только после teardown.

**Impact:** после принятия не остаётся одного однозначного current ADR-контракта для этих security/compatibility guarantees; исторический ADR-006 можно ошибочно считать полностью неактуальным, хотя architecture и STEP-002 продолжают на него опираться.

**Fix direction:** явно определить, какие clauses ADR-006 заменяются, а какие включаются ADR-007 без изменения, либо не supersede ADR-006 целиком и оформить ADR-007 как дополняющее решение. Current traceability должна сохранять все действующие guarantees.

### F-T10 — High — Executable test plan STEP-002 пропускает crash сразу после `attachIntent`

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:65`; `planning/tasks/STEP-002.md:69,86-87`.

**Scenario:** Given ADR handoff требует отдельные boundaries после atomically journaled `attachIntent` и после inert attach, when implementer следует focused-test checklist plan steps 5–6, then crash после `attachIntent` не назван как parameterized fault point и может быть объединён с attach. Именно этот state определяет, требуется ли direct-child proof и как release ведёт себя до membership.

**Impact:** suite может не доказать retained budget и корректный child proof для intent, durable зафиксированного до успешного attach, пропустив premature release либо вечное удержание lease.

**Fix direction:** добавить `attachIntent` как отдельный named crash/restart point в executable plan STEP-002, включая variant с persisted intent до successful attach; проверить отсутствие нового admission/spawn, retained lease и требуемый child proof.

### F-T11 — High — STEP-002 противоречиво задаёт child proof для pre-spawn release

**Location:** `docs/adr/ADR-007-crash-consistent-containment-lifecycle.md:43-55,65-67`; `planning/tasks/STEP-019.md:63-64`; `planning/tasks/STEP-002.md:65,69,83`.

**Scenario:** Given ADR-007 разрешает pre-spawn recovery `RESERVED`/`CREATED`/`BOUND` с `attachIntent=absent` завершить через `noChildEverAttached`, when implementation следует plan step 2, then release разрешён только после unconditional `direct-child reap`. Verification того же STEP одновременно требует no-child receipt без фиктивного reap.

**Impact:** implementation/test oracle неоднозначен: безопасный pre-spawn crash либо навсегда удерживает capacity, либо нарушает собственный plan, синтезируя невозможный reap.

**Fix direction:** синхронизировать plan step 2 с mutually exclusive proofs: `directChildReaped` только при recorded `attachIntent`, `noChildEverAttached` только при доказуемом absent intent; regressions должны отдельно доказывать оба пути и exactly-once release.
